# Document background: a fill for the document, and the eyedropper that picks it

Status: Ready (`adrs.md` and the UX notes of 2026-10-10 exist; delivery: one PR, four milestones, after #79 and #80 merge)
Priority: Should
Origin: Customer (the document may have a fill; the eyedropper for objects picks the background; the eyedropper for the background itself; request of 2026-10-10). Proposals, marked where they occur and in the decisions below (defaults taken by the lead, 2026-10-10): "none" drawn as a checkerboard, the pasteboard is not pickable, the Opacity row, the default colour kept at today's value, the label `set_document_background`.

## User value

As a maker I want the document (the page) to have its own fill, a colour with alpha or none, and I want the eyedropper to pick that colour like any other colour in the drawing, so that I can design on the colour of my material or sheet (black acrylic, kraft paper, a white card), see my artwork against it, and reuse that colour for a stroke or fill with one click.

**What the others do, and what we do differently.** Inkscape's Document Properties has a page background colour with alpha and a checkerboard switch. Illustrator's artboards have no fill; a transparency grid shows on request. Figma has a canvas colour that is not the fill of any frame. LightBurn has no page colour. Differences here:

- The background is edited in the **Document section of the Properties panel**, in the same inline colour block as an object's fill (swatch, eyedropper, 8-digit hex, picker, Opacity). No dialog, no popup (`0017-style-panel-rework`, panel rule).
- **None is drawn as a checkerboard** (the sign for "transparent" everywhere else in the app), so "no background" can never be mistaken for a colour.
- **The eyedropper treats the background as paint.** Over the document area, where no painted object is under the pointer, it picks the background colour, alpha included. The Background block has an eyedropper of its own that picks from the drawing and from the background itself.
- The default is **exactly what the document looks like today**: `--canvas-bg`, `#E8E8EB`, fully opaque. Not white (`docs/design-system.md`, token `--canvas-bg`, "Canvas background"; `0015-document-size-and-rulers` criterion 28). No existing project and no existing golden image changes.
- The background is **a property of the document, not an object**: it cannot be selected, moved, transformed, combined, copied or deleted; resizing the document keeps it.

This spec does not decide whether or how the background is exported, printed or cut (Out of scope). It is stored so those slices can use it.

## Acceptance criteria

Colours are written `#RRGGBBAA`. "The document area" is the closed rectangle from (0, 0) to (width, height) in document coordinates, edges included. "The pasteboard" is everything outside it. "Stored colour" is the value in the document, not a rendered pixel. "Painted" is as defined in `0017-style-panel-rework` criterion 24.

### Part A: the background in the document

1. Given the document model, then the document has a **background** made of a paint, `None` or `Solid`, and a colour (red, green, blue and alpha, the same colour type as an object's fill colour). The colour is kept while the paint is `None`.
2. Given a new project, then the paint is `Solid` and the colour is `#E8E8EBFF` (the value of `--canvas-bg`, alpha 1). Test: the document area of a new project renders as `#E8E8EB`, and the Background hex field shows `#E8E8EBFF`.
3. Given a background, then it is stored in the document root as two registers: `background_paint`, the string `"none"` or `"solid"`, and `background_color`, **one** register holding `[r, g, b, a]` (red, green, blue and alpha together). Red, green and blue are whole numbers from 0 to 255. Alpha is the same 0 to 1 fraction an object's fill stores: `AA/255` from the hex field and the eyedropper, `N/100` from the Opacity field, and nothing is rounded on read (`adrs.md`, decision 2). A register that is absent means its default (`"solid"`; `[232, 232, 235, 1.0]`).
4. Given a project file written by any earlier build (format versions 1 to the current one on `main` before this slice), then it opens with the default background, every object where it was, and **opening writes nothing**: the file is byte-for-byte unchanged on disk after Open without an edit. Test: open a fixture of an older version, compare file hashes before and after.
5. Given this slice, then `format_version` goes to the **next free number at merge** (`specs/README.md`, "`format_version` plan"): 10 if nothing else merges first, otherwise the next free one (0023 groups would take 10). A reader that knows only an older number refuses a file with the new number ("saved by a newer version"), as for every bump. A file of the new version without the registers is valid and means the default. Test: the writer's version constant is compared against the named constant, not a literal.
6. Given Save, Close and Open, then the paint and the colour are the same, with every component exactly as stored (an alpha of 128/255 stays 128/255, it is not rounded to 50 %). A `None` background keeps its colour: after the round trip, pressing Solid shows the same colour as before the save.
7. Given a file in which a background register is present but malformed, then the file is refused as **damaged** with the app's existing damaged-file message, and nothing is written. Validation on open is strict. Malformed means: the paint is not one of the two known strings; the colour is not a list of exactly four entries, three whole numbers from 0 to 255 and one finite number from 0 to 1 (so red given as a fraction such as 0.5 or 1.0 is malformed). Each case has its own fixture and test (`adrs.md`, decision 11: unknown paint, three entries, alpha 1.5, red as a double). This is stricter than the size rule of `0015` criterion 13 (a bad size falls back to A4) by the customer's request. A missing register is never damaged (criterion 4).
8. Given New, then the new project has the default background (criterion 2) whatever the previous project had. Given a project opened after another one, then it shows its own background and nothing of the previous project's. Test: set the background to `#FF0000FF`, then open a file without the registers; the area renders `#E8E8EB`.

### Part B: drawing the background

9. Given the default background, then every pixel of the document area that no object covers is `#E8E8EB`, and every pixel of the pasteboard is `#B8B8BE`, as before this slice. Test: every existing golden image of the renderer passes without being regenerated.
10. Given a `Solid` background with alpha 255, then the document area is painted in that colour and the pasteboard stays `#B8B8BE` (`--pasteboard-bg`, flat, `0015` criterion 28). The edge between them is on whole device pixels (`0015` UX notes, "Pasteboard and document edge"). Test: with `#FF0000FF`, a pixel 1 px inside the corner is `#FF0000` and a pixel 1 px outside is `#B8B8BE`.
11. Given a `Solid` background with alpha below 255, then the colour is composited over the checkerboard of criterion 12, so the maker sees how transparent it is. Test: with `#FF000080` and cells of `#FFFFFF` and `#C9C9CE`, the pixel over a white cell is `#FF7F7F` and over a grey cell `#FF6464`, each within 1 per channel.
12. Given a `None` background, then the document area shows a checkerboard of two tones, `--checker-a` `#FFFFFF` and `--checker-b` `#C9C9CE` (the tokens of `docs/design-system.md` that mean "transparency shows through"). The cells are squares of 8 CSS px, which is `round(8 × devicePixelRatio)` device px (at least 1), so every cell edge is on a whole device pixel; at a fractional ratio the cell rounds (ratio 1.1 gives 9 device px). The size is fixed on screen and **does not change with the zoom**. The pattern is anchored at the document's top-left corner, so it moves with the page on a pan and does not swim. The cell at the corner is `--checker-a`; cells are clipped at the right and bottom edges of the document area (a partial cell is fine). The checkerboard never extends onto the pasteboard or under the rulers. Test, at ratios 1 and 2 and at any zoom: at ratio 1 the pixel 4 px right of and below the corner is `#FFFFFF` and the pixel 12 px right and 4 px below is `#C9C9CE`; at ratio 2 the same points scale to 8 and 24 device px right and 8 below.
13. Given the draw order, then it is: pasteboard, document background (checkerboard first when it is shown), objects, editor overlays (selection, handles, guides, readouts). An object with a fill is drawn over the background and hides it; an object with fill `None` shows the background through. Test: a rectangle with a `#00FF00FF` fill on a `#FF0000FF` background renders green inside and red around it.
14. Given the rulers, the status bar and the panel, then the background changes none of them. Given the background changes (any edit), then the canvas shows the new look in the same frame as the Background block (the panel's preview rule, `0017` criterion 18).

### Part C: the Background block in the Document section

The Document section is shown exactly as `0015` criterion 14a and `0030` criterion 18 say (nothing selected, the Pen has no unfinished path). This spec changes when it is shown in no case.

15. Given the Document section is shown, then it contains a **Background** block: a heading row with the heading "Background" and a Paint group with two items, **None** and **Solid**, pressed to the current paint. Both items are always present. The block is the last one in the section, **below Fit to content**, after a 16 px gap with a 1 px rule. Its title row is the Paint group's row: the heading "Background" at the left and the Paint group right-aligned. The rows above it never move when the block's rows come and go. The block moves 36 px when Fit to content enters or leaves the tree (the object count going between 0 and 1) and in no other case; this never happens while a Background control is in use.
15a. Given the window is 800 x 600 and the Background paint is `Solid`, then the presets, Width, Height, Unit, Fit to content (when present), the Background title row with its Paint group, the Color row and the saturation/value area are in view without scrolling (the area to within 4 px of its bottom edge). The hue slider and Opacity need a scroll of about 70 px (on an empty document, where Fit to content is absent, the hue slider is in view too and only Opacity needs the scroll). The panel scrolls as a whole: no sticky heading, no inner scroll area, no control in the block captures the wheel (over the picker the wheel scrolls the panel), a focused control is scrolled into view with 12 px of scroll padding, and the scroll position returns to the top when the shown section changes (Document, Style, empty). From a window about 670 px high up nothing scrolls. Test: measure the positions at 800 x 600.
16. Given the paint is `Solid`, then the block shows, in this order and with the same rows, sizes and rules as the Fill section of `0017` (rows 2 to 4 of its UX table): the **Color** row (a swatch, an eyedropper button, the hex field), the inline **picker** (a saturation/value area and a hue slider, always visible, no click to reveal), and an **Opacity** value field. Given the paint is `None`, then the block is one row, the heading and the Paint group, and none of the other controls is in the document tree, focusable or in the accessibility tree. The heading and the Paint group do not move when the other controls come and go (`0017` criterion 5), so a mouse press on the switch stays under the pointer.
17. Given the Paint group, when the maker presses None or Solid, then the paint is set in one commit. Given None and then Solid, then the colour returns exactly as it was (`0017` criterion 7). A press on the already pressed item writes nothing.
18. Given the hex field, then it shows the stored colour as `#RRGGBBAA`, upper case, 8 digits, and accepts 3, 4, 6 and 8 digits with or without `#`, in any case, with spaces ignored, exactly as `0017` criteria 11 and 12 define, with the document as the only target (there is no "Mixed" state). 3 and 6 digits keep the alpha. Refused input keeps focus, selects the text, shows "Enter 3, 4, 6 or 8 hex digits" in the error chip and writes nothing. Test: from `#E8E8EBFF`, typing `fff` gives `#FFFFFFFF`; typing `f80c` gives `#FF8800CC`; typing `12345` is refused.
19. Given the Opacity value field, then it follows `0017` criteria 34 to 47 (drag, modifiers, typing, scale, reset slot) with the default 100 %, and edits the same alpha as the last two hex digits, each in its own grid (`0017` criterion 13). Test: typing `2F6FEE80` in the hex gives Opacity 50 with stored alpha 128/255; then typing 50 in Opacity stores 0.5 and the hex reads `#2F6FEE80`.
20. Given the inline picker, then `0017` criteria 17 to 20 apply (drag, one update per frame, one commit on release, Escape reverts, arrow keys 1 % and Shift 10 %, no jump of the hue through grey). The commit changes red, green and blue and keeps the alpha. The "several objects" clause (criterion 21) does not apply.
21. Given the swatch, then it shows the colour at its alpha over the checkerboard of criterion 12, is display only and is not a tab stop. The Tab order in the block is the Paint group (one stop), the eyedropper button, the hex field, the picker area, the hue slider, the Opacity field, as the Fill section has it.
22. Given any edit of the background (Paint, hex, picker, Opacity, eyedropper pick, reset), then it is **one commit**, labelled `set_document_background`, that writes only the register that changed (the paint edit writes `background_paint`; a colour or Opacity edit writes `background_color`). A value equal to the stored one writes nothing and makes no commit. While a drag or an arrow key is held the canvas shows the preview (ephemeral, not in the document); the release or key-up commits once; Escape or a system cancel drops the preview and writes nothing (`0017` criteria 18, 39, 40, 60). Test: during a picker drag the stored registers equal the values before the press; after the release they equal the new colour.
23. Given an edit is running (a drag, an arrow key held, text being typed) when the Document section leaves the tree (for example the selection changes through the keyboard), then a drag or held key still commits to the document and typed text is restored (`0017` criterion 59). An edit never loses its target, because the target is the document.
24. Given the Document section's header, then its subject line stays what `0030` criterion 10a defines, derived from the size only ("A4, portrait", "Custom"). The background does not change it, and the Background block has no subject line of its own. Test: set the background to `#FF0000FF` on a new project; the subject line still reads "A4, portrait".
25. Given a control of the block has keyboard focus and leaves the tree because the paint became `None`, then focus moves to the Background Paint group; after a mouse press focus goes to the canvas (`0017` criteria 1 and 57).
26. Given the block, then no element with role `dialog`, `listbox` or `menu` appears, no control is rendered disabled and nothing opens over the canvas or other panel content, except the text-only tooltips, the validation chip and the eyedropper's readout chip (`0017` criteria 3 and 55). Backspace, Delete and letters typed in any control of the block never reach the canvas (`0017` criterion 57).
27. Given accessible names, then: the group is a `radiogroup` named "Background" with items "None" and "Solid"; the eyedropper button "Pick background color from the drawing" (`aria-pressed` while picking); the hex field "Background color hex (RRGGBBAA)"; the picker controls "Background saturation and value" and "Background hue"; the value field "Background opacity". The screen reader can tell the Background controls from the Stroke and Fill controls, which never share the panel with them (a selection shows Style, no selection shows Document).

### Part D: the eyedropper picks the background

These criteria extend `0017` criteria 22 to 27, which stay as they are for every case in which an object is under the pointer.

28. Given picking is active for the stroke or fill of the selected objects (`0017`), when the maker presses on a point where **a painted stroke or painted fill is under the point** (criterion 24 of `0017`), then the colour of the topmost such object is taken, exactly as before this slice. **Objects keep priority over the background**, including an object that lies partly on the pasteboard. Test: a rectangle with fill `#00FF00FF` on a `#FF0000FF` background; a press inside the rectangle picks `#00FF00FF`.
29. Given picking is active, when the maker presses on a point **inside the document area where no painted object is under the point** and the background paint is `Solid`, then the **stored background colour, alpha included**, is taken and written as the colour of the target (stroke or fill) of all selected objects in one commit, and picking ends. The same rules as `0017` criterion 24 apply to the target: a pick for the stroke turns an off stroke on; a pick for the fill never turns a fill on. Test: background `#FF000080`; a press on empty document area for the stroke of a selected rectangle gives the stroke colour `#FF000080` (not the composited pixel, not `#FF7F7F`), and its stroke Paint is Solid.
30. Given the stored-colour rule, then the picked value never depends on the zoom, the checkerboard, the pixel under the pointer or the antialiasing (`0017` open question 2, option A). Test: the pick at 2 %, 100 % and 8000 % returns the same value.
31. Given an object whose fill is `None` lies over the background, then a press in its interior (away from its stroke) picks the background, because an object with paint `None` is not pickable by that paint (`0017` criterion 24); a press on its stroke picks the stroke colour. Given an object with a fill of opacity 0, then the press picks that fill (`#RRGGBB00`), because a paint with opacity 0 counts as painted.
32. Given the background paint is `None`, when the maker presses on a point inside the document area where no object is painted, then nothing is written and picking stays active (`0017` criterion 25). The readout chip reads "No paint here" (criterion 35).
33. Given a point on the **pasteboard** (outside the document area) where no painted object is under the point, then nothing is picked, nothing is written and picking stays active; the chip reads "No paint here". The pasteboard is app chrome, not a colour of the document (open question 2; this is the default). Test: a press 1 px outside the document edge, with no object there, writes nothing.
34. Given the document area is hit-tested, then a point is inside when `0 <= x <= width` and `0 <= y <= height` in document coordinates, edges included, with no tolerance, evaluated after the object test. The background is never hit-tested by the Select tool (criterion 40).
35. Given picking is active and the pointer rests on a point whose pick would be the background, then the readout chip of `0017` criterion 23 shows, in this order, a 16 px swatch (the colour at its alpha over a checkerboard of 4 px cells), the muted word "Background" and the stored colour: **"Background #RRGGBBAA"** (for example "Background #E8E8EBFF"). For an object's paint the order is the colour, then the muted word, as in `0017`. Where a pick would take an object's paint, the chip is as in `0017` (the colour with "stroke" or "fill"); where nothing would be picked it reads "No paint here" with no swatch. The chip updates at most once per animation frame and still holds no control, takes no focus and no pointer events.
36. Given the Background block's eyedropper button, when it is pressed, then picking starts **for the background colour**, with the cursor, the chip, the cancel rules and the keyboard rules of `0017` criteria 22, 23, 26, 27 and 60 (Escape, tool change, a rail press, a press in the panel other than the button, a second press on the button and a right-click on the canvas end picking and write nothing; pan, zoom and the wheel keep working). The pressed state of this button is the only indication of the target: no banner and no other row appears.
37. Given picking for the background is active, when the maker presses on a point, then the colour is taken by the rules of criteria 28 to 33 (objects first, then the background, nothing on the pasteboard), including the **background's own colour**, and is written as the background colour in one commit (`set_document_background`), keeping the paint `Solid`, and picking ends. A pick that equals the stored colour writes nothing and still ends picking. A pick of a colour with alpha 0 (an object's fill of opacity 0) sets alpha 0 and the document area then shows the checkerboard through a `Solid` paint. Test: a rectangle with stroke `#0000FFCC`; pressing on its stroke with the background eyedropper sets the background to `#0000FFCC`; pressing on the empty area afterwards, with a stroke eyedropper, would give `#0000FFCC` (the new stored value).
38. Given picking is active for the background, then a press on the canvas selects nothing, moves nothing and draws nothing (`0017` criterion 23), so the Document section stays in the panel until picking ends.
39. Given a pick (any target, any source), then the polite status line announces it once through the app's status region (`0017` UX notes, section 5): for the background "Background color set to #RRGGBBAA".

### Part E: the background is not an object

40. Given the background, then it is not selectable and has no bounds. A click, a marquee or a lasso over the document area with the Select tool selects nothing from the background (a click on empty area clears the selection as before); Select all (Ctrl+A) does not include it; the selection box, group box, member boxes, the object count in the subject line, Fit to content (`0015` criterion 23), the Boolean and path operations, the transform handles, Delete, Duplicate and the Move entry never see it. Test: on an empty document with a `#FF0000FF` background, Ctrl+A selects nothing, and the Fit to content button is absent (`0015` criterion 22).
41. Given a drawing or editing tool, then it works over the background exactly as over the previous document colour: no snapping to it, no hint, no warning.
42. Given a resize of the document (a typed size, a preset, the orientation items or Fit to content), then the paint and the colour are unchanged and the fill covers the new document area exactly; the resize commit (`resize_document`, `fit_document_to_content`) writes no background register. Test: with `#FF0000FF`, pick A3 from A4; the area renders red edge to edge in 297 x 420 mm, the registers are unchanged, and the commit changed only size and positions.
43. Given a preset or an orientation press (`0030`), then the background is kept as in criterion 42. Given a unit change (`0015` Part C), then nothing in the background changes.
44. Given Copy and Paste of objects, then the background is not part of the clipboard and a paste never changes it.
45. Given two peers that edit the same document at the same time, then the background merges by register: when both set the colour, both end with the same value, which is one of the two complete colours and never a mix of their channels; when one sets the paint and the other the colour, both end with the new paint and the new colour. Test: peers A and B start from the default, A sets `#112233FF`, B sets `#445566FF` concurrently; after the merge both peers hold the same colour and it is one of the two exactly.
46. Given a Pen with an unfinished path, then its close-target marker (the knockout dot, `0015` criterion 31) over the document area has the fill of the colour behind it: with an opaque `Solid` background the background colour; with `None` or a translucent background the stored colour composited over `--checker-a`, `#FFFFFF`. Over the pasteboard it is as before (`#B8B8BE`).

### Part F: cost and legibility

47. Given the default and any opaque `Solid` background, then the document rectangle is drawn with one command, as before, and the draw list is not longer. Given `None` or a translucent colour, then the checkerboard is **one** extra draw command whatever the zoom and the document size (no geometry per cell). Test: on an empty document, count the artwork layers plus the checkerboard prefix of the draw list for the three cases. `None` has as many layers as an opaque colour, plus the prefix; a translucent colour adds one layer to the prefix case (`adrs.md`, decision 6).
48. Given picking, then the added work per hover is one rectangle containment test after the object test. The existing hover budget of `0017` criterion 23 (at most one hit test per animation frame) holds unchanged.
49. Given an editor overlay (selection line, handle, guide, readout) over a background other than the default, then it keeps the casing rule of `docs/design-system.md` ("Casing over artwork"), which does not depend on the colour behind it: the better of the full-strength accent line and the white casing is at least 2.1:1 against every opaque colour (worst case at relative luminance 0.445) and against both checkerboard cells (2.7:1 on `--checker-b`). Hover and member boxes at 60 to 65 % are weaker, as measured per fill. Contrast numbers measured against `#E8E8EB` elsewhere in the design system hold for the default only.

## Out of scope

- **Export, print and job behaviour of the background**: whether SVG, PNG, PDF, print or a laser job include it, as a rectangle, as page colour or not at all, and what a `None` or translucent background produces. Proposal for that story: the background is exported only when the paint is `Solid` and alpha is above 0, and never becomes a cut or engrave path. `svg-import-export` and `laser-job-preview-and-output` decide. The background is stored so they can use it.
- **Gradients** (removed from the product, `0017`), **background images**, patterns, textures, a placed reference image.
- **A page colour per object, per layer or per group.** One background for the document. Layers (`0039`) may get one later, as its own decision.
- **A "reset to default" button or a "Paper colour" list** (kraft, black acrylic, birch plywood). The Opacity reset of `0017` criterion 61 applies to alpha only. Materials with a colour come with the material database (R-MAT-001) or `color-management`.
- **Palettes, colour history, the old and current swatch pair, other colour models**: `color-management` (R-EDIT-017).
- **Picking the pasteboard colour**, colours outside the app window, a keyboard path for the eyedropper (`0017` criterion 27).
- **Adapting the editor overlays to the background**: selection lines, handles and rulers keep their colours and their casing (criterion 49). A dark theme is a later decision.
- **A setting for the checkerboard** (colours, size, a switch to show it for an opaque background). One look, from the design system.
- **Undo and redo** (`0020`). Each edit is one commit, so undo can take it later.
- **Several pages**: dropped (2026-10-05).

## Open questions

Decided on 2026-10-10 by the lead, taking the default of each. The customer can still change any of them; the text below stays as the record of the options.

Decisions taken: default colour `#E8E8EB` (not white); the pasteboard picks nothing; None is drawn as a checkerboard; both `None` and `Solid` with alpha 0 are kept; the picker is always visible (the Document section scrolls about 70 px at 800 x 600, criterion 15a); the block sits below Fit to content; no shortcut; no edge line on a `None` document; chip word order "Background #RRGGBBAA".

1. **Default colour (criterion 2).** *A (default, recommended):* `#E8E8EBFF`, what the document area looks like today. No existing project, golden image or contrast measurement of the design system changes. *B:* white `#FFFFFFFF`, the colour of paper. Every existing project would open white, every golden image changes, and the measured contrasts of the pasteboard (1.61 to the document) and of the overlays change. A maker can type `FFFFFF` at any time either way.
2. **Pasteboard and the eyedropper (criterion 33).** *A (default, recommended):* the pasteboard picks nothing ("No paint here"). It is app chrome, it is not stored, and it will change with a dark theme. *B:* it picks `#B8B8BEFF`. That puts a colour into the drawing that is not a colour of the document.
3. **How "None" is drawn (criterion 12).** *A (default, recommended):* the checkerboard of `--checker-a` and `--checker-b`. Same sign as the swatches and the cursor chip; the maker cannot take it for a colour. *B:* the previous colour `#E8E8EB`: None and the default look the same, so the maker cannot see the difference. *C:* white. Same problem as B for a white background.
4. **Transparent twice (criteria 1, 15).** `None` and `Solid` with alpha 0 look the same. *Default:* keep both, as the Fill section has them (None hides the colour controls and remembers the colour; Solid at 0 % keeps them). Dropping None would remove one state but would also remove the one-row block.
5. **Panel height (criterion 15).** The Document section is about 352 px with the presets of `0030`. The Background block with Solid adds about 240 px (heading and Paint 28, Color 28, picker 116, Opacity 28, gaps), so the section is about 590 px at Solid and the 800 x 600 viewport (about 546 px) scrolls. *Default:* the picker stays always visible, as decided for the Style section (`0017` open question 6); the ux-engineer chooses the place of the block and says in the UX notes which rows stay in view. *Alternative if the scrolling annoys:* one disclosure arrow that folds the picker, still inline, no popup.

Decided by the product owner (change if you disagree): the Opacity row in the block (alpha has one drag field, as in Fill); one commit label `set_document_background`; the checkerboard cell of 8 CSS px, fixed on screen and anchored at the document corner; the chip text "Background #RRGGBBAA" as asked; picking ends after one pick as for objects; the background colour is one register; a pick for the background keeps the paint `Solid` because the colour controls exist only then; a missing register is the default and a malformed one is damaged.

## UX notes

By `ux-engineer`, 2026-10-10. Numbers and component rows are in `docs/design-system.md`: "Properties panel: Document section" (rows "Background block" to "Background picking"), "Pasteboard and document edge", "Canvas checkerboard", the tokens `--checker-a`, `--checker-b`, `--canvas-bg` and "Casing over artwork". Reference tools: Inkscape puts the page colour in a dialog, Illustrator and Figma have none; here it is a block in the panel the maker already looks at when nothing is selected, built from the parts of the Fill section, so there is nothing new to learn. ### Layout: where the block goes and what stays visible

- **Place: last block of the Document section, below Fit to content**, after a 16px gap with the 1px `--toolbar-icon` at 25% rule (how Fill follows Stroke). Order of the section: header, Paper, Slides, Orientation, rule, Width, Height, Unit, Fit to content, rule, Background. The frequent edits (a format, a size) stay at the top, where they were; a rarely changed fill sits under them. Not above the sizes: it would push Width down by 240px for a control touched once per project.
- **Heights.** Title row 28px (Paint None, the whole block). Solid: 28 + 8 + Color 28 + 8 + picker 116 + 8 + Opacity 28 = **224px**, the same as the Fill section. Section: 352 + 16 + 224 = 592px, 616px with the panel padding (None: 396px).
- **At 800 x 600** (panel viewport about 546px) the default Solid block scrolls the panel by about 70px. Without scrolling the maker sees the presets, Width, Height, Unit, Fit to content, the Background title row with its Paint group, the Color row (swatch, eyedropper, hex) and the saturation/value area (to within 2px of its bottom edge; the implementer measures it). The hue slider and Opacity are one wheel notch away. On an empty document (no Fit row) the hue slider is in view too and only Opacity is cut. From a window about 670px high up nothing scrolls.
- **Decision (open question 5): the picker stays always visible**, 244 x 96 plus the hue slider, the same component and size as in Style. Reasons: one picker behaviour in the app (the Style decision of `0017`, U1); no new disclosure component and no state to remember per session; the cost is scrolling only on the smallest window; every control the maker needs for the common job (type a hex, pick from the drawing) is above the fold. Alternative in the open questions.
- **Scrolling.** One scroll for the whole panel (`overflow-y: auto`, as today): no inner scroll area, **no sticky header** (a sticky "Document" row would take 32px of the 546 to repeat what the maker just scrolled past, and the subject line is not needed down there). `scroll-padding-block: 12px` so a focus ring is never cut when focus scrolls a control into view. No control in the block captures the wheel: over the picker area the wheel scrolls the panel. The scroll position resets to the top when the shown section changes (Document, Style, empty), so Style never opens scrolled.
- **Fit to content moves the block.** The Fit row is removed on a document without objects, so the block sits 36px higher there. This happens only when the object count goes between 0 and 1, never while a Background control is in use (a drag, typing, picking), so it is accepted. Reserving the space would put a hole in an empty document.
- **Paint row.** The title "Background" (12px semibold, `--toolbar-icon`) does not fit the 60px label column of the Style sections (about 66px wide), so in this block the title sits at the left and the Paint group **None | Solid** (2 x 44px, the Style `ToggleGroup`) is right-aligned to the content edge (x 156 to 244). The row is the anchor: it does not move when the rows below come and go.
- **Rows below the title** are the Fill section's, unchanged: Color (swatch 28, eyedropper 28, hex), picker (area 244 x 96, hue 244 x 12), Opacity (value field 244 x 28, reset to 100 %).
- **Subject line.** Unchanged ("A4, portrait" / "Custom"; criterion 24). The background is not part of the size, and a second state in the header would make "Custom" ambiguous.
- **Resize and presets.** Nothing in the block moves or changes on a size change. On canvas the document edges move and the artwork does not (`0015`); the checkerboard re-anchors to the new corner in the same frame, with no animation. A fill colour covers the new area edge to edge, because it is the document's, not an object's.

### The canvas: checkerboard and edge

- **Look.** Cells of `--checker-a` `#FFFFFF` and `--checker-b` `#C9C9CE`, the tokens of the swatches, so "transparent" has one look in the whole app. Squares of **8 CSS px, round(8 x devicePixelRatio) device px**, so every cell edge is on a whole device pixel and nothing blurs. Fixed on screen, not scaled with the zoom: the cell is not a ruler, and a zoomed cell would read as part of the drawing. Anchored at the document's top-left corner, cell (0, 0) is `--checker-a`, clipped at the right and bottom edges (a partial cell is fine), never drawn on the pasteboard or under the rulers. The swatch and the chip keep their 7px and 4px cells, which fit 28px and 16px.
- **Contrast.** Measured (WCAG): `--checker-a` to `--pasteboard-bg` `#B8B8BE` 1.98:1, `--checker-b` to the pasteboard 1.20:1, a to b 1.65:1. The edge is therefore carried by the pattern ending, half of its length at 1.2:1. That is weaker than the default edge (`--canvas-bg` to pasteboard, 1.61:1) and is accepted: the white cells break the line every 8px, and an object on the page is still bounded by its own stroke. If a review finds the edge too weak, the fix is the 1px edge line of the `0015` open question, not a darker `--checker-b` (the swatches share the token). Black (21:1 on a, 12.7:1 on b), `--toolbar-icon` and `--accent` (4.5:1 on a, 2.7:1 on b) stay legible over the pattern. A white-filled object without stroke on a checkerboard is bounded only by the grey cells; that is how every checkerboard behaves.
- **Translucent Solid** is drawn over the same pattern, so the maker reads the alpha from how much of the pattern shows through; the swatch does the same at 28px.
- **Overlays.** The casing rule does not depend on the background: `docs/design-system.md` states the guarantee (criterion 49). The Pen close-target dot (criterion 46) is a white knockout with its usual ring on `None` and on a translucent background; over the pattern it reads as a dot because of its ring, not its fill.

### Eyedropper

- **Starting.** The Background block's eyedropper is the Fill section's button (28px, `Pipette`, pressed look while picking, `aria-pressed`). The maker sees which colour is being set by the pressed button in the only colour block on the panel: while picking for the background the Document section stays and no Style section is there, so it is never ambiguous. No extra banner, no second line in the block: a row that appears would shift the block (panel rule), and the chip already names its source.
- **Cursor.** The same eyedropper cursor (24px, black with white casing, hotspot at the tip) over the whole canvas, pasteboard included. It does not change over "no paint" so that the cursor does not flicker while the maker moves; the chip says so.
- **Chip** (the "Live transform readout" surface, 12px up and right of the pointer, flips at the edges, `pointer-events: none`, no focus). Three states: **object paint** unchanged from `0017`: swatch 16, `#RRGGBBAA`, muted "stroke" or "fill" after it; **background**: swatch 16 (the stored colour at its alpha over the 4px checkerboard; `None`-like alpha 0 shows only the pattern), the muted word "Background" (`--panel-muted-fg`, 12px), 4px, then `#RRGGBBAA` (12px tabular `--toolbar-icon`), e.g. "Background #E8E8EBFF"; **nothing**: "No paint here", no swatch, over the pasteboard and over a `None` background with no object. The word comes first for the background because that is the text the customer asked for and because it names a place; for an object it is a kind of paint, after the number. Width about 170px at the longest. Accessible text is the same string; the chip is `aria-hidden` and the status line announces the result (criterion 39).
- **After a pick** the colour is in the hex field, the swatch and the picker thumbs, like a typed colour; focus goes to the canvas; picking ends. A pick equal to the stored colour ends picking and writes nothing (criterion 37).
- **Escape, tool change, right-click, a press elsewhere in the panel:** as `0017`. A press on the collapse tab ends picking too.

### Behaviour, keys, names

- **Tab order:** Paper, Slides, Orientation, Width, Height, Unit, Fit to content, Background Paint (one stop), eyedropper, hex, picker area, hue, Opacity. `Shift+Ctrl+F` still focuses Width. No new shortcut: setting the background is once per project, and a key for it would be one more thing to remember (open question 3).
- **Focus after Paint None:** the Paint group keeps focus on a key press (criterion 25); a mouse press returns focus to the canvas. Panel focus ring, hover and pressed looks are the Fill section's; nothing in the block is disabled or greyed.
- **Hidden, not disabled:** with `None` the whole colour part leaves the tree; the colour is remembered and returns on Solid. Nothing in the block says that the colour is remembered, as in the Fill section.
- **Accessible names** as criterion 27. The title "Background" labels the radiogroup (`aria-labelledby`), items "None" and "Solid". The swatch is `aria-hidden`; the hex field announces the 8-digit value. The checkerboard is a canvas drawing and has no text alternative; the Paint group's state is the text.
- **Tooltips** (Radix, 400ms, `side="left"`, text only, also on keyboard focus): Paint group "Fill of the whole document. None shows a checkerboard. The background is not an object; it cannot be selected or moved."; eyedropper "Pick a color from the drawing (Esc cancels)" (as Fill; the accessible name carries "background"); Opacity as every value field "Drag to change, click to type. Shift: coarse. Ctrl: fine. Ctrl+Backspace: reset." The hex field has none, as in Style.
- **Validation chip** for the hex: "Enter 3, 4, 6 or 8 hex digits"; for Opacity "Enter a number from 0 to 100". As Style, below the field, no row shifts.
- **Empty and large documents.** An empty document shows the block like any other (the default is a real fill). A large document costs nothing extra: one rectangle containment test per hover (criterion 48), one extra draw command for the checkerboard (criterion 47). Undo does not exist yet; each edit is one commit.
- **Not promised in the UI.** The panel says nothing about export, print or cut. Whether a laser job includes the background is decided later (Out of scope); until then the tooltip says only that it is not an object.

### Open design questions (defaults taken)

1. **Picker always visible (default) or one disclosure arrow.** The default costs a 70px scroll at 800 x 600 and nothing from a window of about 670px. With an arrow, folded by default, the section is 468px and never scrolls, but it hides the picker in the one place where the maker mostly types a hex or picks, adds a component and a state, and gives the app two picker behaviours. Take the arrow if scrolling annoys after trying it (the `0017` position).
2. **Block below Fit to content (default) or between Unit and Fit.** Below moves the block 36px when Fit appears; between keeps the block still but separates Fit from the size fields it belongs to and breaks "Fit is the last row".
3. **Shortcut to focus the Background Paint group.** Default none. Candidate if wanted: `Shift+Ctrl+B`.
4. **Edge of a `None` document** (1.2:1 on half the edge). Default: no edge line. Alternative: the 1px edge line of `0015`, which would also change the default look.
5. **Chip word order.** Default "Background #RRGGBBAA" (the customer's text) against "#RRGGBBAA stroke" for objects. Alternative: "#E8E8EBFF background", one order everywhere.
